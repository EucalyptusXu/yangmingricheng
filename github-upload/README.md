# 阳明日程 · 知行合一

一个把「王阳明」嵌进日程管理的安卓应用。**419 条语录全部存在手机本地**，记录的事项里出现什么关键词，首页就换一句对得上的话；完成得多还是落下的多，语气也不一样——而且不会在你累的时候教训你。

---

## 一、它做了什么

### 核心功能

| 功能 | 在哪 | 说明 |
|---|---|---|
| **添加日程** | 右下角「＋」 | 标题、日期、起止时间、备注、重复规则、提醒开关。**输入标题时实时预告首页会变成哪一句** |
| **编辑 / 删除** | 日程详情 →「编辑」 | 改时间不用删了重建；删除可撤销 |
| **日程提醒** | 添加页 / 今日页 | 准时或提前 5/10/15/30/60 分钟。走系统通知，通知正文就是那句配对出的语录 |
| **逾期顺延** | 今日页顶部 | 过去没划掉的事自动汇总（**只算不重复的日程**——每天的习惯昨天没做不算欠债）。可单条「已做 / 顺延」，也可一键全部顺延到今天，带撤销 |
| **日程管理** | 「日历」页 | 日 / 周 / 月 / 年 四个维度；周视图是七天完成度柱状，月视图是格子日历带完成度圆点，年视图是 365 天热力图 + 12 个月缩略图 |
| **完成度统计** | 「数据」页 | 年度总数 / 已完成 / 完成率、连续达标天数、近 30 天趋势、事项标签分布 |
| **语录库** | 「我的」页 | 419 条，按 10 个主题筛选、可搜索，分页加载 |

### 语录是怎么"适配"的

这是应用的核心。不是随机抽签，是一条带**语气底线**的链路：

```
输入标题 / 备注
   ↓  词典扫描（长词优先，避免「会」抢占「会议」）
标签集合，例如「产品需求评审会」→ {工作: 1}
   ↓  叠加完成状态权重：未完成 ×1.4，已完成 ×0.7
   ↓  近义扩展（×0.45）
      稀薄标签自动带上语义邻居，例如「金钱」→ 名利 / 欲望 / 得失 / 知足
      这是解决"标签稀疏导致推得不着边际"的结构性手段
   ↓
判断状态：完成率 + 是否有事项过时
   ↓
【语气底线 —— 硬过滤，不是加权】
   今天已经落下事情、而用户自己并没有表达"要往前推"的意图时，
   直接排除掉全部「律己型」语录（"志不立天下无可成之事"这种）。
   加权做不到这个保证，所以这里是硬排除。
   空白的一天不受限制：还没开始，立个意思是合适的。
   ↓
打分排序（内容相关度 × 语气权重 × 时段权重）+ 稳定伪随机
   ↓
首页那一句 +「为什么是它」的解释
```

**「为什么是它」只给情绪，不给实现。** 比如："今天有点沉。（有 2 件已经过了时点还悬着）所以挑了句站在你这边的话。" —— 刻意不显示"识别到：工作、复盘"这类信息。一旦用户看到关键词匹配的过程，"它懂我"就退化成"关键词匹配"了。

### 反馈闭环

语录卡上有两个按钮：

- **「说得对」** —— 记录偏好，今天不再重复给同一句
- **「今天不想听这句」** —— 立刻换一句，且这句今天不会再出现（负反馈）

反馈按天存在本地，只保留最近 30 天。原来的「换一句」按钮被删掉了——既然说是根据你的事推的，就不该能随便换；能换等于承认随机。

## 二、语料库

### 规模与组织

**419 条**，按来源分四册，全部本地存储（`js/data/`，共 108KB，随 APK 一起打包，运行时零网络请求）：

| 文件 | 内容 | 条数 |
|---|---|---|
| `quotes-01-chuanxilu.js` | 《传习录》《大学问》《教条示龙场诸生》《示弟立志说》 | 150 |
| `quotes-02-prose.js` | 书信、杂著、序记、乡约 +《传习录》补遗 | 126 |
| `quotes-03-poems.js` | 诗作（据《王阳明全集》诗部） | 127 |
| `quotes-04-supplement.js` | 补遗，专补稀薄标签 | 16 |
| | **合计** | **419** |

每条的数据结构：

```js
{ id:'q001', theme:'立志', tone:'strict', src:'《教条示龙场诸生》',
  text:'志不立，天下无可成之事。', tags:['立志','方向','目标','计划'] }
```

- `theme` —— 10 个主题之一（立志 / 知行 / 磨练 / 自省 / 为学 / 心境 / 日常 / 山水 / 人情 / 处世），决定配色与默认语气
- `tone` —— 语气，**引擎的关键字段**
  - `strict` 律己：在要求你（"你应该""不做就不好"）
  - `warm` 体谅：在理解你（"慢一点也行""这样也可以"）
  - `clear` 说明：把事情讲明白（"事情是这样的""这样做或那样做"）
- `tags` —— 匹配挂钩，平均每条 3.89 个，**改这里就能改推荐行为**

### 语气配平（这是本次刻意做的）

之前 50 条版本里，律己型占 56%，「日常」只有 1 条。用户下班累到不想动时打开看到"志不立，天下无可成之事"——不是被鼓励，是被指责。

现在：**律己 35% / 体谅 41% / 说明 24%**。加上引擎的语气底线，累的时候永远拿不到说教。

### ⚠️ 关于校对（重要，请务必看）

这批语料是我从王阳明的著作里辑录的，**但请在做正式发布前做一次逐条校对**。

理由很直白：部分条目来自长期流传的版本，字句可能与中华书局点校本《王阳明全集》有出入；个别条目的篇名归属也可能不够精确。我已经做的保障是：

- 出处统一按《篇名》标注，格式规整，便于逐条比对
- 语料是**纯 JS 数组**，一行一条，替换/删改不需要懂代码
- 附了一个校对工具，改完跑一遍就知道有没有改坏

```bash
cd yangming-schedule
node tools/audit-corpus.js          # 体检
node tools/audit-corpus.js --strict # 有警告就返回非零退出码，可挂 CI
```

它会检查：条数、id 与正文是否重复、必填字段、标签是否越界、主题是否都有配置、语气比例是否失衡、主题分布、兜底池候选是否充足、别名表指向的标签有没有语料承接。当前状态：**错误 0 · 警告 0**。

## 三、技术选型

**为什么是 WebView 而不是原生 Compose？**

| 方案 | 优点 | 代价 |
|---|---|---|
| 纯原生 Kotlin/Compose | 性能最好 | 每改一版 UI 都要重新编译安装，改一行字等 1 分钟 |
| **本方案：H5 内核 + 原生壳** | 改 UI 秒级生效；同一份代码也能跑手机浏览器；日历/热力图这类密集渲染用 DOM 最省事 | 首屏多约 200ms |
| Flutter / RN | 折中 | 引入几百 MB 工具链 |

日程类应用的本质是"表单 + 列表 + 图表"，没有重动画和重传感器，WebView 完全够用，而迭代速度的收益是实打实的。

**原生只做浏览器做不了的三件事**：本地通知、精确闹钟（`AlarmManager`）、开机后恢复闹钟。通过一个叫 `YMBridge` 的桥暴露给网页。

**提醒可靠性**：网页端每次打开、每次数据变动，都会重算**未来 30 天**的提醒（上限 200 条）并整体覆盖原生闹钟。所以只要一个月内打开过一次，提醒就不会断。原生侧在开机、改时间、换时区、应用更新后都会重放存档。

## 五、怎么跑起来

### 1. 只看网页版（最快）

```bash
cd yangming-schedule
python3 -m http.server 8080
# 打开 http://localhost:8080
```
或直接双击 `index.html`。

### 2. 打包成 APK —— 三条路

**路径 A：有 Android Studio（推荐）**
1. Open → 选 `android` 目录
2. 等 Gradle 与 SDK 下载完
3. Build → Build Bundle(s) / APK(s) → Build APK(s)
4. 产物：`android/app/build/outputs/apk/debug/app-debug.apk`

**路径 B：只有命令行**

```bash
cd android
./sync-web.sh              # 先同步网页资源
gradle assembleDebug       # 需要 JDK 17 + Android SDK
adb install app/build/outputs/apk/debug/app-debug.apk
```

**路径 C：什么都没有（纯云端）——你当前这台机器就属于这种**

这台机器**没有可用的 git**（`/usr/bin/git` 只是占位，`xcode-select` 没装），所以给了两条上传路子：

**C-1 · 不装任何东西（推荐先用这条）**

根目录下的 `github-upload/` 是可直接上传的干净副本，已剔除内部工作目录和构建产物。改完代码后跑一次 `bash ./build-upload.sh` 重建它再上传，保证副本永远最新：

1. 打开 github.com → 右上角 `+` → **New repository** → 填名字 → **Create**
2. 在新仓库页面点 **uploading an existing file**
3. 把 `github-upload` 这个**文件夹本身**拖进浏览器上传区（macOS 上直接拖文件夹就会带上 `.github/` 和 `.gitignore` 这些隐藏文件）
4. 填一句 commit message → **Commit changes**
5. 进 **Actions** 标签页 → 左侧选 **Build APK** → 若没自动跑就点 **Run workflow**
6. 等 3~5 分钟变绿勾 → 点进那次运行 → 页面**拉到最下面** → **Artifacts** → 下载 `yangming-schedule-debug`
7. 下载到的是 zip，解开就是 `app-debug.apk`

**C-2 · 装 git（一次性解决，之后都方便）**

终端里跑 `xcode-select --install`，会弹窗，点「安装」，等 5~10 分钟。装完之后：

```bash
cd github-upload
git init && git add -A && git status     # ← 先看一遍 status
git commit -m "阳明日程 v1.0.0"
git branch -M main
git remote add origin <你的仓库地址>
git push -u origin main
```

**两种推法都能出包**，仓库里放了两条 workflow：

| 推什么 | 生效的 workflow | 差别 |
|---|---|---|
| 整个项目（`github-upload/` 的内容） | `.github/workflows/build-apk.yml` | 会先跑 `sync-web.sh` 再从网页源码构建，**永远不会出现"忘了同步 assets"的坏包** |
| 只推 `android/` | `android/.github/workflows/build-apk.yml` | 更精简；但网页源码不在仓库里，只能看到打包后的副本 |

> **Artifacts 需要登录 GitHub 才能下载。** 要发给别人、或者想要一个不用登录的下载链接，就在仓库里建一个 Release，把 apk 作为附件传上去。

### 3. 装到手机后必做的两件事

1. 「我的」页 → 点**「申请通知权限」**
2. 点**「测试提醒」**，确认通知栏弹出「阳明日程 · 提醒测试」

没弹出来就按顺序排查：
- 系统设置 → 应用 → 阳明日程 → 通知：是不是被关了
- 系统设置 → 电池 → 应用启动管理：设为「手动管理」并允许后台活动（国产 ROM 默认会杀后台，这是提醒失效的最常见原因）
- Android 12+：设置 → 应用 → 特殊权限 → 闹钟和提醒 → 允许。不允许也不会丢提醒，只是时间会飘几分钟

## 七、数据存在哪

**全部在手机本地的 localStorage，不上传任何服务器，应用没有网络权限。**

- 换手机：「我的 → 导出备份」复制那串 JSON，新机器上「导入备份」粘回去
- 首次运行的演示数据**不会自动塞**，要先在引导卡片上点「先用示例看看」；装进去之后顶部会有提示条和一键清空按钮，清空只删示例、不动你自己加的数据

## 八、还没做的

- 只做了「轻提醒」，没有闹钟式全屏提醒（`setAlarmClock`）
- 通知上没有「完成 / 延后」按钮（延后有了，完成需要在原生侧写一个待办队列回传 WebView）
- 深色模式没做，应用固定宣纸浅色（`forceDark = FORCE_DARK_OFF`）
- 没有桌面小组件
- 没有搜索日程（只在语录库里能搜）
- 没有云同步

**发布前要处理**
- 换上你自己的 keystore（`android/app/build.gradle.kts`，现在没 keystore 时会回落到 debug 签名）
- 上架 Google Play 需要说明 `SCHEDULE_EXACT_ALARM` 的用途
- 语料做一次逐条校对

**下一步优先级**
1. 早晨固定推送一句（基于昨天完成情况 + 今天日程）—— 这是留存的最高杠杆，也是产品定位该走的方向
2. 每周回顾页，做成可分享的图 —— 唯一的自然传播点
3. 云同步 / 账号 —— 日程数据用户的心理预期是"不能丢"
